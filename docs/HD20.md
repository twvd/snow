# HD20 (Directly Connected Disk) support

Snow can attach an Apple HD20-compatible hard disk to the external floppy port. Apple called
this a *Directly Connected Disk* (DCD). The 512Ke, Plus, SE, SE FDHD, Classic and Portable
carry the DCD driver in their `.Sony` driver, so they mount the disk and boot from it with no
extra software. That gives the 512Ke, which has no SCSI, a hard disk, in the same way a BMOW
Floppy Emu in HD20 mode, a TashTwenty or a FujiNet does on real hardware.

The 128K and 512K Macs need the HD20 INIT from a boot floppy, as on real hardware. The Mac II,
IIx, IIcx, II FDHD and SE/30 ROMs have no DCD support either; on real hardware they need
Apple's MacIIHD20 INIT. Snow behaves the same: those Macs don't see an HD20 without it.

## Using it

In the **Drives** menu, the HD20 entries attach a disk image (read/write or read-only) to the
end of the daisy chain, or detach one. Up to four can be attached, the most the `.Sony` driver
takes. The Mac looks for HD20s when it starts up, so attach them before booting, or restart.

A workspace (`.snoww`) keeps the attached HD20s in chain order. Like the other paths in a
workspace, `image` is relative to the workspace file:

```json
{
  "rom_path": "rom/MacPlus-v3.ROM",
  "model": "Early512Ke",
  "hd20": [
    { "image": "disks/system608.hda" },
    { "image": "disks/apps.dsk", "read_only": true }
  ]
}
```

Leaving the field out means no HD20, so older workspaces load unchanged.

- **Images.** Use a raw image of 512-byte blocks:
  - A bare HFS (or MFS) volume, such as a Floppy Emu, Mini vMac or Basilisk II `.dsk`/`.hfv`.
  - A partitioned SCSI-style image, such as a BlueSCSI `.hda` with an Apple partition map. For
    these, the first `Apple_HFS` partition is presented as the volume.
- **Size.** The protocol counts blocks in 24 bits. The practical limit is the 2 GB that System
  6/7 HFS supports.
- **Writes.** A read/write image is memory-mapped, so writes go straight to the file. Don't
  run two emulators on the same image. A read-only image reports itself write-protected, so
  the Mac mounts the volume locked, and the device refuses any write that still arrives.
- **Save states.** Save states hold the HD20 images, the same way they hold SCSI disk images.
  A loaded state works on a temporary copy, not the original file.
- **External floppy.** The HD20s sit at the head of the daisy chain on the external port. An
  external floppy drive still works behind them, as it does on the real hardware.
- **Memory.** A 512Ke has 512K of RAM. A System Folder set up for a 4 MB Plus (AppleShare,
  MacTCP, EtherTalk, MultiFinder and similar) runs out of memory there. Expect "Memory Manager
  error" or a crash at the desktop. Boot such a disk with a trimmed System Folder, the same as on
  real hardware.

## Protocol

This is a summary of what Snow implements. The behaviour follows the Mac Plus ROM's `.Sony`
driver, which wins wherever it disagrees with Apple's 1985 documents.

### Lines and states

A DCD answers only on the external drive enable (`!ENBL2`) and ignores SEL/HEADSEL. CA2:CA1:CA0
form a 3-bit state. The device drives RD (the IWM SENSE input, status bit 7) according to the
state:

| State | Mac to device                  | RD carries                    |
| ----- | ------------------------------ | ----------------------------- |
| 0     | data, holdoff                  | data                          |
| 1     | data transfer                  | data                          |
| 2     | idle                           | `/HSHK` (0 = asserted)        |
| 3     | request / end of transfer      | `/HSHK`                       |
| 4     | reset                          | 0                             |
| 5     | identification                 | 0                             |
| 6, 7  | identification                 | 1                             |

To detect a DCD, the ROM reads state 7 = 1 (a floppy reads 0 there), state 6 = 1, then state
5 = 0. DCDs become drives 3 to 6 with driver refnum −2.

**Daisy chain.** The ROM selects drive *n* by turning the enable off and on, then giving *n*−3
LSTRB (CA3) pulses in state 7. Each pulse makes the selected device pass the enable on to the
next device. Snow keeps a chain position: dropping the enable resets it to 0, and each rising
edge of LSTRB while an HD20 is selected advances it (accessing the LSTRB-high address again
while LSTRB is already high is not a new pulse). Past the last HD20 the external floppy drive
(if any) answers. Nothing may answer as a DCD at position 4, or the ROM decides the chain can't
pass the enable on and installs only one DCD, so Snow takes at most four.

**Disk in place.** Every 30 ticks the ROM reads state 2 for a DCD it hasn't mounted yet. An idle
device (`/HSHK` high) posts the disk-inserted event.

### Wire format

Bytes go through the IWM at the floppy bit rate: 2.04 µs per bit cell, 16 C8M clocks, so 128
C8M clocks (16.34 µs) per byte. The wire rate is fixed in time, so on a C16M bus (the Portable
and the Mac II family) a byte takes 256 bus clocks. The ROM sets IWM mode `$1F`. Every byte on
the wire has its MSB set.

- **Mac to device:** `AA`, `80+groups sent`, `80+groups expected back`, then the groups, then
  two `00` flush bytes that the device ignores.
- **Device to Mac:** `AA`, then the groups.
- **7-to-8 groups:** 7 payload bytes become 7 bytes `80 | (b >> 1)` plus one byte
  `80 | LSBs`. The first payload byte's LSB is bit 0 of the LSB byte. The Mac sends the LSB byte
  first in each group; the device sends it last.
- **Checksum:** the last payload byte makes the sum of all payload bytes 0 (mod 256).
- **Example:** the status command `03 00 00 00 00 00 FD` goes out as
  `AA 81 B1 C1 81 80 80 80 80 80 FE`, which matches a capture from a real Mac.

### Handshake

**Command (Mac to device):**

1. The Mac checks that `/HSHK` is high in state 2.
2. It raises CA0 (state 3), and the device asserts `/HSHK`.
3. In state 1 the Mac writes the transfer.
4. In state 3 the device releases `/HSHK`.
5. In state 2 the device processes the command and asserts `/HSHK` once it has a response.

**Response (device to Mac):**

1. The Mac goes through state 3 to state 1 and clears the data register.
2. The device sends `AA` and the groups at the byte rate.
3. It releases `/HSHK` when the last byte reaches the data register: the Mac checks it once, at
   once, after reading that byte (error `$25`).
4. Back in state 2, a multi-block read asserts `/HSHK` again for the next block.

**Holdoff.** During a transfer the ROM polls the SCC. Mouse movement on a 512Ke/Plus is enough.
When an SCC interrupt is pending, the Mac drops to state 0 in the middle of a group, finishes
that group, services the interrupt, returns to state 1 and carries on with `AA` and the next
group. It never resends a group. The same holds in both directions.

**Reset.** State 4 resets the device. The ROM holds it for 100 ms, waits 2 s, then waits for
`/HSHK` high in state 2. It uses this only to recover from errors.

### Commands

Every response starts with `cmd | 80`, then a count, then 4 status bytes; all zero means
success. To flag a failure Snow sets the first status byte to `$81`. The Plus ROM fails an
operation when bit 0 of that byte is set (or the byte is `$0A`) and ignores the other three,
which matches the HD20 firmware's own "operation failed" bit; the 1985 spec says bit 7. `$81`
satisfies both. After three failed tries the ROM resets the device, tries once more, and then
returns `readErr` or `writErr`. A failed read block still carries the full 539 bytes, and the
reply ends at that block, because the ROM stops there.

| Command       | Mac sends                                             | Device answers                                                              |
| ------------- | ----------------------------------------------------- | --------------------------------------------------------------------------- |
| `00` read     | `00 N blk(3) 00 cks` (1 group)                        | one 539-byte reply per block: `80 n status(4) tags(20) data(512) cks`, n counting down N..1 |
| `01` write    | `01 N blk(3) 00 tags(20) data(512) cks` (77 groups)   | `81 N status(4) cks`                                                        |
| `41` continue | the next block of a write, `41 n ...`                 | `81 n status(4) cks`; the block number is the previous one + 1              |
| `02`/`42`     | write-verify, same as write (the ROM never uses it)   | `82 ...`                                                                    |
| `03` status   | `03 xx 00 00 00 00 cks`                               | 343 bytes: device type, manufacturer, characteristics, block count, icon, mask, "Where" string |
| `19`/`1A`     | format / verify format                                | `99`/`9A` with status 0                                                     |
| bad checksum  |                                                       | NAK: `7F 00 00 00 00 00 81`; the ROM retries                                |

A command covers at most 255 blocks. The ROM splits larger requests itself.

The status reply has these fields:

| Offset  | Field                                                          |
| ------- | -------------------------------------------------------------- |
| 6       | device type `0001`                                             |
| 8       | manufacturer `0001`                                            |
| 10      | characteristics `$E6`, or `$CE` when write-protected           |
| 11      | block count (24-bit)                                           |
| 14      | spare and bad block counts, zero                               |
| 70      | 32×32 icon                                                     |
| 198     | 32×32 mask                                                     |
| 326     | Pascal "Where" string for Get Info (`Snow HD20`)               |

The characteristics bits are `80` mountable, `40` readable, `20` writable, `08`
write-protected, `04` icon included and `02` disk in place.

## Implementation in Snow

- `core/src/mac/swim/dcd.rs` holds the device:
  - the handshake state machine, 7-to-8 encoding, commands and partition map lookup;
  - unit tests covering encoding, the wire vectors, status, multi-block reads, writes with
    continuation, NAK, holdoff in both directions, reset and the partition map.
- `core/src/mac/swim/{mod,iwm}.rs` handle the IWM side:
  - the chain position and routing SENSE, LSTRB and phase changes to the device while it is
    selected;
  - a byte-level tick (`dcd_tick`) that shifts written bytes out to the device and latches its
    bytes into the data register every 16.34 µs (`dcd::ticks_per_byte`). This avoids the floppy path's weak-bit noise,
    which would create phantom bytes on an idle line.
- `Emulator::attach_hd20_image` attaches an image; the frontend calls it for the workspace's
  `hd20` list and the Drives menu (through `EmulatorCommand::Hd20Attach`/`Hd20Detach`).
- `core/src/emulator/save.rs` stores each HD20 image after the SCSI images in a save state.

Verified in Snow:

- **Models:** 512Ke (all three 128K ROM versions), Plus (all three), SE, SE FDHD, Classic and
  Portable boot System 6.0.8 from an HD20 to the Finder, mount a second HD20 next to it, and
  mount an HD20 next to a floppy they booted from. The Plus mounts four. The Mac II (both ROMs,
  with the 8-24 or Toby card), II FDHD, IIx, IIcx and SE/30 ignore the HD20, as their ROMs do.
  The Portable needs the real-time byte rate: with bytes every 128 C16M clocks (twice the real
  rate) its ROM misses some and retries the first status command forever.
- **512Ke (512K RAM):** boots System 6.0.8 from a 2 GB partitioned image to the Finder.
- **Plus (4 MB):** boots the untrimmed image to the Finder.
- **Read-only:** the 2 GB image boots read-only to the Finder with its windows showing the
  lock, and the file is unchanged afterwards.
- **Save states:** a state saved after creating a folder, loaded after creating another,
  brings back the first folder only; the restored HD20 then takes new writes.
- **Writes:** a Finder Duplicate of a 335 KB application gave identical forks.
- **Holdoff:** constant mouse movement during boot caused thousands of holdoffs with no protocol
  errors or retries.
